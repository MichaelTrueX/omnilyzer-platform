### First investigation decision: priority P0

Perform only a **separately scoped read-only incident triage**. Authorized information is (a) public/nonsecret workflow step metadata, (b) historical broker and ingress service status/audit and available journal metadata without message bodies or sensitive identifiers, and (c) read-only source/fixture comparisons of code that was actually deployed at the incident commit. Do not generate or capture a new JWT, display Authorization/OIDC headers, reveal JTI/sub/claims, change OIDC trust or audience policy, consume replay state, dispatch a workflow, or resubmit the HTTPS POST.

Prioritize evidence in this order:

1. Establish which component emitted the response using retained nonsecret correlation and status metadata, if any; explicitly mark journal inaccessible/rotated if it cannot be recovered. Never infer the cause from HTTP code alone.
2. If the response is conclusively broker-originated, identify a **coarse, nonsecret** existing rejection class from available evidence: ingress request validation, OIDC/claims, registry binding, canonical request, replay or executor handoff. A missing observation remains UNKNOWN.
3. Compare the exact historical GitHub run SHA, request digest and source version with the activated service's historically pinned SHA; investigate release-manifest and Forgejo registry hashes without access to secrets or a live authorization attempt.
4. Reproduce **only the proved boundary** with synthetic offline fixtures, add a negative test at the owning layer, and require a separately reviewed corrective change. If incident evidence cannot distinguish the boundary, report BLOCKED and request a distinct authorization for any later diagnostic observation.
